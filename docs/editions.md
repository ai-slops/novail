# Snapshot Exports and Immutable Editions

## Meaning and scope

A snapshot is a fixed selection of working manuscript content adopted by a human. An edition separately preserves the selected snapshot's title, subtitle, scene order, and text. **Publishing an edition stores it inside the NOVAIL workspace**; it does not publish, upload, or disclose it externally.

Creating an edition does not move the main working copy's head. Later editing, candidate adoption, restoration, or switching works never changes an existing edition. There is no API to edit, delete, or overwrite an edition. A revised edition is a new record that references the prior edition.

The current authorization model is the single-user local Owner mode described in the README. This feature does not implement multi-user authentication or authorization checks.

## API

Mutations require a UUID `Idempotency-Key`. GET requests never create an edition or change the manuscript.

New mutations identify the reviewed branch with `X-Novail-Branch-Id`, and idempotency records are bound to the work and branch. An edition can be published only from a snapshot visible on the selected branch, while an already published edition is readable throughout the work. See `branches.md` for the legacy headerless single-branch compatibility policy.

| Route | Action |
|---|---|
| `GET /api/export-preview?snapshotId=...` | Read the selected Snapshot's manifest, scene list and length, and latest Edition |
| `GET /api/export?snapshotId=...&format=markdown` | Download the selected Snapshot's manuscript |
| `GET /api/export?format=docx` | Download the current head as DOCX |
| `GET /api/export?snapshotId=...&format=manifest` | Download source hashes and ordering information for the selected Snapshot |
| `POST /api/editions` | Record a new Edition after explicit approval |
| `GET /api/editions` | List Editions for the current work |
| `GET /api/editions/{id}` | Read an Edition summary and frozen manifest |
| `GET /api/editions/{id}/export?format=docx` | Generate a download from that immutable Edition |

Export formats are `markdown`, `docx`, and `manifest`. Omitting the format uses Markdown; omitting the snapshot uses the current head. Saved draft workspaces and unadopted candidates are never exported.

```json
{
  "title": "First Edition",
  "snapshotId": "<selected Snapshot id>",
  "expectedHead": "<head when review began>",
  "approvedManifestHash": "<SHA-256 from the preview>",
  "revisionOf": null,
  "approvedPreviousManifestHash": null,
  "decision": "publish",
  "policyVersion": 1
}
```

When an Edition already exists, `revisionOf` and `approvedPreviousManifestHash` must contain the preview's `latestEdition.id` and `latestEdition.manifestHash`. A request that has not acknowledged the latest Edition is rejected. Consequently, if two windows approve the same predecessor concurrently, the later request must review again after the first succeeds.

## Approval and preservation

- The preview hash is bound to canonical JSON containing the project ID, Snapshot ID, title, subtitle, scene order, scene titles and numbers, text SHA-256 values, and lengths.
- On publication, NOVAIL recalculates the same content and compares it with the approved hash. A changed expected head returns `STALE_HEAD`; a changed content hash returns `APPROVAL_MISMATCH`.
- A missing or stale prior-Edition approval is rejected with `EDITION_APPROVAL_REQUIRED`.
- An empty Snapshot without manuscript text is rejected with `EMPTY_MANUSCRIPT`.
- Edition data, the explicit approval event, publication audit, and outbox event are recorded in the same storage transaction.
- Edition export reads the stored Edition document, not the current manuscript. Source or manifest integrity errors are exposed as `EDITION_INTEGRITY_ERROR`.
- Switching works preserves the Edition collection with its work; an Edition ID from another work cannot be read.
- Switching branches preserves published Editions, and a new Edition records its origin in `sourceBranchId`. The new field is not retroactively added to existing Edition hashes.
- The UI retains the head observed when the approval screen opened. A failure never silently substitutes the latest head into the approval.

## Document formats

DOCX output is an OOXML document generated by the `docx` package. It stores the title, subtitle, chapter headings, paragraphs, and intra-paragraph line breaks. It requests a Batang-family font but does not embed font files, so the receiving environment may substitute another font.

File names use ASCII identifiers and extensions, such as `novail-edition-<id>.docx`. Korean manuscript titles remain unchanged inside the document and manifest. This interoperability policy avoids Chromium behavior that reduces some UTF-8 `Content-Disposition` filenames to `download`.

NOVAIL guarantees source hashes and content reproducibility, not byte-for-byte identical DOCX archives, whose ZIP metadata can differ. Invalid Unicode blocks export and publication. Control characters that OOXML cannot represent return an explicit DOCX error. Source text is never silently deleted or changed.
